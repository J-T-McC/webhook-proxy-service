Plans live at `docs/plans/plan-NN-<slug>.md` (not the template's `<feature-slug>-plan.md`); ADRs at `docs/architecture/adr-NNN-<slug>.md`. Both start from the plugin templates, with house additions the Task Planner and Reviewer expect.

## Plan sections

- **`## Test strategy`** between Implementation Notes and Handoff, tests grouped by AC and named per acceptance criterion. Not in the plugin template.
- **`Handoff → Owner-approval flags (✋)`** — a numbered list of exactly what needs Owner sign-off, each item stating its precise shape (e.g. the verbatim column definition). **Write the heading even when there is nothing outstanding**; a vanished or absent flag list reads like an oversight.
- A plan that rules on something the PRD or design left silent gets an explicit **named ruling section**, stating why it stays inside the upstream artifact's assumptions and therefore does not route back upstream.

## Certification and the Owner gate

Self-certification is partial and the Status line says so. Triggers observed: any ADR, any new table/column/index, any irreversible operation, any new at-rest copy of sensitive data. Data-model changes are never PE-self-certified.

Three shapes:

1. **No flags** — Status reads "Approved (Principal-Engineer self-certified) — **in full**"; the Certification paragraph says explicitly there is no carve-out; the flags section lists the gate struck through with its Accepted date; add a short *Why no new ADR* paragraph walking each candidate against the ADR bar.
2. **Flags outstanding** — say so in the **Status line itself**, not only in Handoff ("self-certified **except** the two items at Owner-approval flags"); enumerate the whole data-model change set in **one clearly-marked § Data Model block** so the Owner rules on it at once; pair every data-model gate with an explicit **"Explicitly *not* in the change set"** list (verified item by item) and a security assessment — the additive-only claim is what makes the gate a single reversible decision; add the mirror paragraph *Why an ADR was warranted here when the previous item needed none*; Next Agent reads "Task Planner — **after** Owner approval of items N". Sequence **§ Milestones** so the gate-blocked ones are named and say how many are not blocked, so a pending gate does not stall the Task Planner.
3. **Flags without an ADR** — a real shape: the gates *are* the decision record and an ADR would restate them. Invert the paragraph (*Why no ADR was warranted here, when the previous item needed one*), then walk every ADR the feature touches one by one and say explicitly that it needs no amendment. Imprecise-but-not-contradicted wording in an Accepted ADR is **not** grounds to supersede it.

Where a design spec is approved *with corrections held by the Designer*, write the plan against the **approval note** (it governs over the spec body) and say so in the header and certification. Where the spec's flagged calls are **contingencies whose trigger the PM assigned to the PE**, pull them explicitly: name the call, state which branch it resolves to, and state the user-visible consequence, so the Designer and Reviewer do not have to infer it.

## Revisions

`## Revision A`/`B` sections sit at the top, **most recent first**, with a line saying the earlier one is unchanged; a `Revised:` clause joins the header bullets. Rulings are **appended by number** with *(Added YYYY-MM-DD — Revision B)*; earlier rulings are amended **in place** with *(Amended … — Revision B)*; milestones are appended, never renumbered, with a line on how the new one orders; each revision gets its own dated `### Re-certification at Revision X` **below** the original Certification, which is kept. ACs are never renumbered. The Owner-flag list is restated **in full** in the plan — it is the single place the Owner reads it.

Occasions and what each must state:

- **Owner amendment mid-design** — a `## Revision A — what the ruling changed here` table (*prior position → now*) at the top of every artifact it touches.
- **The PE's own post-certification ruling** (a downstream question doc a fully-approved plan cannot answer as written): the re-certification names **plan authority under the delegated gate, not an Owner ruling, and says none was sought**, and states explicitly that **no already-ruled Owner flag reopens**. Put the "why this needs no Owner gate and no ADR" walk **inside the new ruling**, against `CLAUDE.md`'s major-decision list item by item, then add one line for it to the existing *Why no ADR* list. Where the ruling has a user-visible shape the spec constrains, resolve it by **reusing the approved template with a new value** rather than authoring copy — that is what keeps it off the Designer's desk; say so.
- **A PM amendment onto an already-implemented plan**: say in the re-certification that **carrying a PM amendment is not making a requirement** (the PM ruled the obligation and assigned the mechanism), and when it creates task material fitting no existing task, name the split in § Handoff rather than letting the Senior Developer infer it. If a binding property the amendment states is **already false in the certified plan**, say plainly that the divergence pre-dates the amendment and fix it in a numbered ruling — that is the walk being checkable rather than trusted.
- **An Owner ruling landing post-review** (a review Major routed back because a standing plan ruling forbade the fix): a **plan** ruling is rewritten **in place** — only ratified ADRs get supersession-by-new-file. Revision rows name the review finding each closes; alternatives the Owner considered and rejected are recorded **by name** so they are not re-proposed. State explicitly, even when the answer is "nothing changes", whether each affected **ADR decision** needs amending (walk them one by one — "considered, not overlooked" is what the Reviewer checks for) and whether any approved **copy** needs changing (if it does, that is the PM's call — route it, never rewrite it).
- **Purely additive revision** (plan approved, nothing in it becomes false): say **"purely additive: no existing ruling, gate, milestone, ADR or approval is altered"** in the `Revised:` bullet and under the table; carry Validation, Test strategy and Implementation Notes material **inside** the Revision section as labelled additions ("the section above is unchanged") so certified sections are never edited; where a **§ Explicitly out of scope** bullet is now false, append an inline *(No longer out of scope — superseded by § Revision A ruling N)* annotation and **keep the bullet's own words**, which still record why the plan withheld it at certification. Close with a **Task material** paragraph naming what the unblocked task now needs.
- **Nothing changes yet** — an approved plan gets a `## Pointer to ADR-NNN (Proposed)` section, not a Revision: say "this is a pointer, not a revision" in the first line, list the passages that *would* go stale, state each remains accurate as certified, and add **no re-certification**. A revision letter implies a ruling moved, and none has while the ADR is Proposed.

## ADR supersession

- Revise a **Proposed** ADR in place. Reverse an **Accepted** one only via a **new superseding ADR**.
- **Partial supersession**: the old ADR keeps its file, status and full text, and gains inline `[Pn — SUPERSEDED by ADR-NNN]` blockquotes (`[Pn — PROPOSED supersession by ADR-NNN (pending Owner approval)]` while the new ADR is still Proposed) plus one sub-bullet under its Status line. Verify with `git diff --numstat` that those edits are **pure insertions, zero deletions** — the checkable form of "additive pointer, not a rewrite".
- The superseding ADR carries a **`## Positions superseded` table** with a row per position, each **named (P3, P4, "Decisions 3 and 4"), quoted verbatim, and given its replacement**, plus a **"Not superseded, and named because each looks as though it should be"** list underneath — that list is what stops a reader over-reading the change. Where a superseded bullet's **premise** is wrong rather than its conclusion, correct the premise explicitly ("a signature header carries a digest, not a key"): a Reviewer can apply a corrected premise to a case they have never seen, which a conclusion does not give them.
- Where the ADR only **amends** a prior ADR's meaning rather than reversing a position, annotate it inline as a **PROPOSED amendment, explicitly "not a supersession"**, and keep it out of the Positions-superseded table's supersession column.
- When an Owner ruling licenses reversing ratified positions, open with a **`## The product position this ADR renders`** section quoting the ruling once and enumerating its consequences — **a settled position, not a chronology**.
- **Full supersession on a capability withdrawal**: the retired ADR gets a `SUPERSEDED IN FULL by …` sub-bullet saying it "keeps its file, its Accepted status and its full text as the record of what was built and why". **Then check what cites it** — a decision stated once and cited elsewhere is orphaned by retirement; fix with a `CARRIED FORWARD into ADR-NNN Decision N, which is now its normative record` pointer, a full restatement in the new ADR, and a re-pointing bullet on the citing ADR. Where a new decision **contains** an earlier one rather than reversing it, say so in those words and supersede only its **boundary** and its **safety argument**. **Confirm the surviving decisions explicitly** ("Decisions 2 and 3 stand, whole and operative"), and where a superseded neighbour makes a survivor's argument stronger, say that too. **Rule what stays at the level of the method, not the class**, with a table of member → what depends on it, whenever a shared service is purpose-parameterised. **Rule migrations on "rows are not schema"**: an in-place edit of an unmerged migration converges no database that already ran it and cannot express a data deletion, so a new migration wins even on an unmerged branch; reject expand-and-contract by name when nothing reads the columns concurrently; write `down()` **honest rather than symmetric**, enumerating what it restores (a shape) and what it cannot (values, secrets, code), because a symmetric-looking `down()` invites the belief that a rollback recovers configuration. **Say that discarded work was correct when it was built** — naming completed tasks as built-and-removed rather than as gaps lets the Reviewer read the diff as a deletion, not an omission.

## Handling Owner rulings

- **Quote the Owner's requirement verbatim** as a blockquote — it is the bar being ruled against, and paraphrase loses the qualifier. If the phrasing turns on a qualifier, **enumerate what falls inside and outside it in a table** rather than asserting compliance. Where two Owner requirements pull against each other, say so in one line up front and show the chosen option satisfies both.
- When a new decision **withdraws** an Owner gate, say "withdrawn, nothing replaces it" explicitly. When the ruling names the gated thing in its own words, record `Owner-approval flags (✋): none outstanding`, quote the phrase, and enumerate precisely what it resolved to plus an "explicitly *not* in the change set" list — the gate is discharged, not skipped.
- Where a prior § Alternatives bullet is now adopted, mark it `[ADOPTED — this bullet's original "rejected" position is superseded …]` and **keep the wrong reasoning visible with the correction** rather than deleting it. On acceptance, rewrite every inline `PROPOSED supersession` annotation to `[Pn — SUPERSEDED by ADR-NNN (Accepted, Project Owner <date>)]`, move the Status bullet to `Accepted — Project Owner, <date>` with revisions as sub-bullets, and grep for `pending Owner approval` / `until this ADR is Accepted`, which hide in the Positions-superseded prose.
- **When the Owner suggests a mechanism that works but still loses, say so in those words** ("the trait is not broken here, and the ruling does not rest on pretending it is"). Enumerate what it *does* satisfy first, verified item by item; correct any factually wrong premise in the question rather than answering around it; then give reasons that will still read as reasons in a year (it removes nothing, it re-opens an inconsistency, it moves failure handling outside code we own, it forecloses a seam) over vendor quirks. Prefer rejecting on **failure direction** where possible — "a lost boolean costs a second click, a collapsed absent-versus-empty distinction destroys a secret". When a vendor claim cannot be verified (package not in the tree), say so and make the argument not depend on it.
- **When the Owner *directs* a mechanism mid-flight, present it as a CHOICE at the gate, not as pre-approved**: the directed option as **RECOMMENDED** with honest costs, the rejected alternative enumerated in full so a `no` is immediately buildable, and the phrase "the alternative ruling available to the Owner". **Couple related flags explicitly** so the Owner is not approving a schema whose premise they may reject. Where the directed model does not fit one member of the set, say so and keep that member out rather than forcing all three in.
- **"The storage model is general, the behaviour is narrow"** is the reusable resolution when a direction implies more capability than an approved AC permits: write it down as the resolution, make the *write path* enforce the AC so it stays literally true, make both *read paths* assume no number, and route the "should the cap change?" question to the PM rather than widening an approved criterion on an inferred reading.
- **When the Owner defers the detail of a principle** ("we can define rules later"), record the principle and say what is missing — do not pick the threshold. State that the boundary needs a number to be usable as a test, that the number is the Owner's once a concrete case exists, and show the refinement changes no existing entry, so the deferral costs nothing now.
- **When a decision's literal value is the Owner's but its principle is yours**, ship the principle with a find-and-replace placeholder (`<BRAND>`); the flag says "a value they supply, not a decision to ratify". When the value arrives, fold it in as decided and **delete the placeholder scaffolding** — a settled document should not narrate that it was once pending. For an option the Owner floats and withdraws, remove it from § Alternatives entirely rather than recording it as considered-and-rejected, but **keep any neighbouring rejection that prevents a real defect**. The test is whether a future reader could re-propose something harmful, not whether the option was discussed.
- **A time-critical-before-merge decision earns its own `#### Sequencing` subsection**: what the change costs before the merge (nothing) and after (a breaking change), why no mechanism softens it (no wire version negotiation, no notification surface, no record of who is affected), and that **the sequencing is part of what the Owner is approving**.
- **An Owner ruling that lands mid-design and contradicts an approved PRD and design spec** gets no Revision section — an uncertified plan is written to the ruling in the first place. Five moves that made it checkable: a **banner at the head of every affected artifact** quoting the ruling verbatim and naming the question doc; **build the backend to the ruling and STOP at the surface**, because a displaced screen is the Designer's and is downstream of a PM amendment; **split the milestone** so the blocked half is the only thing waiting and says what blocks it; a **question document to the PM enumerating exhaustively what goes stale**, AC by AC and screen by screen, with an "unchanged, and worth confirming explicitly" column; and name the **one substantive trade-off** the amendment should be ruled with in view rather than letting the PM inherit it. Never edit the PRD or the design spec.

## Other artifact shapes

- **A defect-driven ADR with no PRD behind it is legitimate.** The `Feature:` bullet says "none" and names how it surfaced; there is **no plan** (inventing `plan-NN` for a bug is wrong — bugs route flat to the Senior Developer, whose `docs/fixes/` record is written on implementation); the whole implementation change set goes in § Impact under a "Code — the complete change set" heading precise enough for the Senior Developer, plus a tests subsection naming which existing tests are **superseded rather than weakened**. Lead with a numbered, plain-language **restatement of the guarantee the system is meant to provide**, written so the Owner can confirm or correct it rather than infer it from mechanism — and where a candidate fix would change that guarantee, say so and **stop**: a requirements change is not the PE's to make even when the Owner's own sentence appears to invite it.
- **A feasibility study is a legitimate fourth PE artifact**, neither plan nor ADR. Filed in `docs/architecture/` as `prd-NN-<slug>-feasibility.md`; the Status line must say in its first words that it is informational — not a decision, not a plan, no ADR, approves nothing, reinterprets nothing. Writing one is **not** planning against an unapproved PRD, and saying so in the header is what keeps it from reading that way. Quote the Owner's request **verbatim** up front; restate the model under test as a **table of axes with AC numbers** and say plainly what would count as failure; carry a **per-item confidence marker** with an explicit "what still needs verifying against the live source", and state once, loudly, that illustrative values are not real test vectors — a confidently wrong example is worse than a marked-uncertain one; give the **negative results equal weight and their own Part**, one block each naming which axis is violated and what supporting it would cost; give a coverage **count plus the caveats that stop it being over-read** rather than a bare percentage. Route every gap found as a **numbered question to the PM**, listed in the study so the Owner sees what they would be approving *with*. Close with an explicit **§ What this study does not do**.
