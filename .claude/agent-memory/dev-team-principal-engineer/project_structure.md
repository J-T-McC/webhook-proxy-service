**ADRs live in `docs/architecture/`**, named `adr-NNN-<slug>.md` (not `docs/adr/` — task prompts sometimes say that; the real convention is `docs/architecture/`). Sequential; ADR-001..018 exist as of 2026-08-25. Template: dev-team plugin `templates/adr.md` (sections: Question, Decision, Alternatives, Reasoning, Impact). Status starts **Proposed**, becomes **Accepted** on Project Owner approval.

**Ingest→delivery dispatch seam (ADR-001/005/007) — two run-sync-or-queue `lorisleiva/laravel-actions`:** `App\Actions\ProcessIngestedWebhook` (pipeline-level: runs the whole native `Illuminate\Pipeline\Pipeline` over one in-memory `PipelineContext`) and `App\Actions\DeliverToDestination` (per-destination). `::run` = sync inline; `::dispatch` = queued. Steps (e.g. `DeliverStep`) are `AsObject`, never queued individually. Gotcha: **`webhook_events` is raw-only immutable by construction (ADR-010)** — it cannot hold dispatch/processing/claim state, so any per-event ordering/claim state (e.g. #4 FIFO) needs a **sidecar table**, and queued jobs should dispatch **by reference** (`ingest_id`, rebuild `PipelineContext` from the `webhook_events` row on the worker) rather than serialize the `Proxy` model or the raw body (up to the ADR-006 body cap). `delivery_attempts` is payload-free (ADR-003). Data-model changes (new columns/tables) are a **CLAUDE.md Owner-approval gate** — never PE-self-certified.

**Anything that MUST happen before the upstream 2xx cannot live inside the `ProcessIngestedWebhook` pipeline — it belongs in the ingest handler, pre-dispatch.** `ProcessIngestedWebhook` is the ADR-005 dispatch-timing seam and since #4 it is dispatched async, so a pipeline step runs *after* the response has been returned. Ingest hot path (`IngestController`): resolve proxy by SHA-256 token hash (team-unscoped, SoftDeletes still applies, 404 on miss) → build `PipelineContext` (shared `ingest_id`) → `ResponseResolver::resolve($proxy)` (config-only, ADR-004) → dispatch → return. This is exactly why ADR-010 moved raw capture out of `PipelineFactory`'s commented enhanced-only `CaptureRawStep` and into a synchronous pre-dispatch step: capture-before-response (PRD-03 AC5) is always-on and cannot be a pipeline step.

**Payload-storage table topology (gotchas that bite any lifecycle/GC work):**
- `webhook_events.body` is **`LONGBLOB` added via a raw `DB::statement('ALTER TABLE …')`**, not Blueprint — `$table->binary()` maps to MySQL `BLOB` (64 KiB), too small for the `encrypted` cast envelope (~35% overhead) at the ADR-006 body cap. Any new payload-content column must repeat this. `byte_size` is always the **plaintext** length, computed before the cast. **Consequence for the whole project: the migration set is MySQL-only and cannot run on SQLite at all** — the `AFTER` clause alone is a parse error there, and three more migrations (`2026_08_05_000001`, `2026_08_05_000002`, `2026_08_12_000004`) use raw MySQL DDL too. `.env.example`/`config/database.php` still *default* to `sqlite`, which is a trap, not a working default: a local `.env` must switch to `mysql`. `./vendor/bin/sail test` (compose.yaml, MySQL 8.4; CI is MySQL 8.0) is the only way the suite runs, so **any dual-engine/portability claim has to be verified at the query-builder level, never by running the suite on SQLite**.
- **A MySQL `json` column can never carry Laravel's `encrypted*` cast.** `webhook_events.headers` is `json`; MySQL validates JSON on write and the cast emits a base64 envelope ⇒ error 3140 on every write. Encrypting any `json` column means a type change to `MEDIUMTEXT` (not `TEXT` — 64 KiB minus ~35% envelope is a silent-truncation cliff) plus a drop-and-re-add, since existing plaintext rows can't be decrypted by the new cast. `content_type` is denormalised into its own column by `WebhookEventCapture::contentTypeFrom()` from the **in-memory** header array before any cast — so it is unaffected by header casts and survives header erasure.
- Every read of `webhook_events.headers` is an Eloquent attribute access; ADR-008 forwarding filters in memory (`DeliveryUnit::forwardHeaders()` over a constant `STRIPPED_HEADERS`). **No `whereJson*`/`JSON_EXTRACT`/header index exists anywhere** in `app/`, `database/`, `tests/` — verified 2026-08-05. `DeliverStep` passes the *same* header array to every destination; only `method` varies per destination (`destinations.http_method`).
- `fifo_dispatches.webhook_event_id` is **`constrained()` = RESTRICT** (as are all `team_id`/`proxy_id` FKs on `webhook_events`/`delivery_attempts`/`fifo_dispatches`). Deleting a `webhook_events` row therefore **fails** unless its `fifo_dispatches` row is deleted first — useful as a fail-loud safety net, fatal if unnoticed.
- `delivery_attempts` reaches an event only through **`ingest_id` (plain uuid column, no FK, plain index)** — so attempt rows are constraint-decoupled from event rows and survive an event delete automatically (ADR-003's "attempt records on their own lifecycle" is structural).
- `webhook_events` indexes are `(team_id, created_at)` and `(proxy_id, created_at)` — a bare `created_at` range scan has no index; scan per team/proxy.
- The `AdvanceProxyFifoQueue` claim locks only `status IN (pending, claimed)` rows under `(proxy_id, status, webhook_event_id)`; work touching only `settled` rows occupies a disjoint index range.

**Mode / enhanced-configuration seams (verify before designing any mode-conditional behaviour):**
- `proxies.mode` is read **behaviourally in exactly one place**: `PipelineFactory::stepsFor()` (two `ProxyMode::Enhanced` branches over the same `$proxy`). Every other `mode` hit in `app/` is CRUD/validation/cast/serialization — grep `ProxyMode|->mode` to re-verify cheaply. Enhanced-only *steps* are gated structurally by composition; enhanced-only *configuration* (retry policy, later #8 maps) is gated at **resolution time** inside its single resolver service, because it is consulted outside the pipeline (settle time, delayed retries) and can never be a step.
- **Single-resolver services are the choke points**: `RetryPolicy` (nominally the only reader of the two `proxies.retry_*` columns and of `config('retry.*')`), `StoredPayloadLookup` (only interpreter of `dispatched_payloads.body IS NULL` and of `payload_cleaned_at`), `RetentionPolicy`. Guard new `config()` reads with the `positiveConfigInt()` fail-loud idiom. Two standing breaches to check before leaning on the invariant: `SweepDueRetries` reads `retry.sweep_grace_seconds` directly (blank env ⇒ `(int)'' = 0` ⇒ cutoff `now()` ⇒ sweeps every retrying delivery every minute), and `ProxyResource` reads the two retry columns directly.
- **`ProxyResource` is one class serving three surfaces** — `index()`, `show()` **and** `edit()`. Anything added to it lands on read *and* write surfaces at once; splitting a write-only field means a second resource class, not a flag. `create()` renders no proxy resource at all (Create.vue hard-codes the blank initial state).
- **Frontend display helpers key off `null`, not off mode**: `proxyRetryAttemptLimitDisplay(null)` renders `5 (default)`, a configured `5` renders bare `5`. So a resource that emits the *effective* value silently changes the Show card's rendering for every unconfigured proxy — emit `null` to mean "the system default governs".
- **`ProxyForm.vue`'s two retry fields have two distinct provenances, and conflating them destroys user data.** A **mount seed** (`props.initial.retry*`, served by `ProxyFormResource`; never mutated, so always available to restore from) vs **in-session typed** input. `watch(isEnhanced, …)` fires only on an in-session mode **change**, never on mount. It shipped with only a *down* arm (clear on Enhanced→Simple); with no *up* arm, an abandoned in-session downgrade (design-07 Flow C step 3 — an explicitly designed path) re-rendered the fieldset blank and the next Enhanced save wrote NULL over the persisted policy. That was review-07's Major, and plan-07 § Technical ruling 4 originally *forbade* fixing it by calling the lost values "in-session typed" — check a ruling's framing against a real reproduction before treating it as binding. The ruling now requires a symmetric up arm re-seeding from `props.initial` with the mount-time `?? ''` normalisation, **unconditionally** (idempotent, and makes the Create and NULL-column cases fall out with no branch — never write a default literal into a field, or an unconfigured proxy silently becomes a configured one). The submit `form.transform()` keys off the **submitted mode**, never field state — that, not the clearing, is what keeps `prohibited_if:mode,simple` satisfiable.
- **Nothing snapshots mode or policy.** Queued jobs are by-reference (`ingestId`/`dispatchUuid`, `deliveryId`/`attemptNumber`); the proxy is re-loaded per run/settle, so "current config governs" is structural. `DeliverToDestination` compares `attemptNumber >= limit` (not `==`), so a shrinking limit terminalizes instead of looping.
- **Gotcha:** `Delivery::proxy()` / `DeliveryAttempt` relations are plain `belongsTo` while `Proxy` uses `SoftDeletes` → `$delivery->proxy` is **null** for a soft-deleted proxy and blows up at runtime in `settleDelivery()`/`DeliveryResource`; PHPStan can't see it (`@property-read Proxy $proxy`). `ProcessIngestedWebhook` is the correct precedent (`Proxy::withTrashed()->findOrFail`).

**A pipeline step that returns `$ctx` without `$next` strands the dispatch — and on FIFO that is fatal.** `ProcessIngestedWebhook` creates the `deliveries` rows (`pending`) *before* running the pipeline, so any step that short-circuits leaves them non-terminal. `AdvanceProxyFifoQueue::settleOrHold()` then parks the `fifo_dispatches` row at `awaiting_retry` **with no lease and no retry schedule** — `SweepStalledFifoDispatches` pass (b) skips the proxy (a held row exists) and pass (c) won't release it (deliveries non-terminal) — so the proxy's line stalls **permanently** and hold **H2 (no age escape)** immortalizes every one of its payloads. Async strands more quietly (badge reads pending forever; H5 still releases). Any new short-circuiting step must first CAS the dispatch's `pending`/`retrying` deliveries → `failed` (+ `DeliveryExhausted` once per affected row, **no** `delivery_attempts` row — the `RetryDelivery::terminalizeCleaned()` precedent); `settleOrHold`/`fifo_dispatches` then need no touching. **`CaptureDispatchedStep`'s cleaned-parent short-circuit (`:70-74`) has this bug today** — narrow (GC must erase *during* a dispatch), unfixed as of 2026-08-26.

**Retry ≠ replay, mechanically.** `RetryDelivery` re-sends `StoredPayloadLookup::dispatchedBytesFor()` — the *recorded dispatched bytes* — so retries never re-run the pipeline and never re-apply a transform. Replay mints a new `dispatch_uuid` and re-runs `ProcessIngestedWebhook` over the whole pipeline from the raw capture. Consequence for any transform seam (#8/#9/#10): a retry after a config edit re-sends the old shape, a replay sends the new one — and re-transforming on retry is *excluded*, not merely undesirable, because the bytes would then differ from `dispatched_payloads.body` (breaks PRD-05/ADR-013's "what is stored is what was sent") and fixing that needs a mid-retention rewrite. `dispatched_payloads` is `UNIQUE(webhook_event_id)`, so a replay **overwrites** it — the store is already last-dispatch-wins.

**Column-type choices that bite later:** prefer `string(32)` + a backed PHP enum cast over the house `enum(...)` column when the value set is meant to grow (adding a case then costs no migration); prefer `longText` + `array` cast over MySQL `json` for anything #10 might later encrypt (a `json` column can never carry an `encrypted*` cast — see the `headers` gotcha above). MySQL **and** SQLite ignore NULLs in unique indexes, so `nullable_boolean` + `UNIQUE(parent_id, flag)` is a portable partial-unique index for "at most one X per parent".

**Retention GC hold set (`PurgeExpiredPayloads::applyHolds()`) — gotchas for any lifecycle work:**
- Six conjunctive holds H0–H5, written **once** and applied to both the selection `SELECT` and the erase `UPDATE`'s own `WHERE` (the compare-and-set). H5 arrived with #6/ADR-015 D7. Never add a hold to only one of the two.
- **One config knob, two different anchors.** `retention.dispatch_horizon_minutes` bounds H4 against `webhook_events.created_at` **and** H5's `pending` clause against `deliveries.created_at`. Because any collectable event is already ≥ the retention window old, **H4's age branch is unreachable in practice** — the knob materially governs H5 only.
- **Corollary that traps people:** for the *original* dispatch, `deliveries` rows are created at ingest, so the H5 age test runs at ingest+window — **no horizon value can ever close an original-dispatch hold gap**; it's unbounded-hold or nothing. Tuning the horizon only helps rows created *late* (replay dispatches, whose `deliveries` rows are minted at replay time).
- **Unbounded holds are rejected by name, three times** (ADR-012 §Alternatives, ADR-015 D7, ADR-016 D2): a never-settling row immortalizes a payload, contra PRD-05 AC6. Don't re-propose one.
- **Nothing terminalizes a stranded Async `pending` delivery.** `SweepDueRetries` touches only `retrying`; `SweepStalledFifoDispatches` pass (c) only *reads* non-terminal deliveries. FIFO self-heals (lease reaper → re-`DeliverStep` inline), Async does not. Assume `pending` can persist forever on Async.
- Async attempt-1 jobs (`DeliverStep` → `DeliverToDestination`) **carry their bytes** in the `DeliveryUnit`; only `ProcessIngestedWebhook` (ingest entry *and* replay) re-reads the stored row. That asymmetry is what makes most GC-vs-dispatch races harmless — if attempt-1 ever moves to by-reference, every such argument inverts.

**Read/aggregation seams over the fact tables (verified 2026-08-26 for #11):**
- **`ApplyTeamScope` registers `TeamScope` on `Proxy`, `Destination` and `DeliveryAttempt` only — NOT on `Delivery` and NOT on `WebhookEvent`.** Half the delivery facts are therefore unscoped inside the team-prefixed group; any query over `deliveries`/`webhook_events` must carry its own `team_id`. Leaning on the middleware gives a right answer for attempt-grained figures and a wrong one for delivery-grained ones.
- **A terminal/resolved row's `updated_at` is frozen, on both fact tables, and that is what makes it usable as a time anchor.** `deliveries`: every write is a CAS keyed on `pending`/`retrying` (`DeliverToDestination::transition()`, `RetryDelivery`'s exhaustion CAS). `delivery_attempts`: created `dispatched`, settled once in `send()`, and `resume()` returns early unless still `dispatched`. GC writes neither. A blind `save()` on either table would silently move history.
- **`delivery_attempts.ingest_id` is the only join that reaches *every* attempt of an event** — replay dispatches under the **event's existing `ingest_id`** (`ProxyEventReplayController`), and pre-#6 rows have `delivery_id` NULL. Joining through `deliveries` silently drops pre-#6 rows. Indexed, so `webhook_events.ingest_id IN (subquery on delivery_attempts)` is cheap.
- **The two counting units live in two disjoint tables** (`deliveries` vs `delivery_attempts`), so "never reconciled against each other" and the pre-#6 include/exclude split are structural — no filter clause to forget.
- **`ProxyResource.destinations` loads live destinations only** — a surface that must show soft-deleted destinations (history/analytics) needs its own row set, not the resource. Adding to `ProxyResource` also hits `edit()` (see the three-surfaces note above).
- **Neither MySQL 8.0 nor SQLite has a percentile function.** Portable *exact* percentile = count `n`, then `ORDER BY col LIMIT 1 OFFSET CEIL(p*n)-1` (nearest rank). No window function needed.
- The shipped Events list (`ProxyEventController::index`) carries **no query filter at all**; its Vue pagination navigates `props.events.links` via `router.get`, so any added filter needs `->withQueryString()` or page 2 drops it.
- **The analytics window is built in three places and two of them disagree.** `DeliveryStatistics::windowStart()` is a rolling `now - interval`; `seriesWindowStart()` is calendar-day aligned (`startOfDay()->subDays(days-1)`); `ProxyEventController` builds a third rolling copy. So the trend series and the headline beside it cover **different spans** — the headline counts records no bucket in the chart covers. Also why a 24h window rendered **one point**: day-aligned start + `days()===1`. Any bucket/window work must collapse these onto one definition (`AnalyticsWindow`), or the chart and the number keep describing different traffic.
- **Neither MySQL 8.0 nor SQLite has a portable hour-truncating function** (`DATE()` is portable, `DATE_FORMAT`/`strftime` are not). Options: a leading `SUBSTRING(col,1,13)` of the implicit datetime→string rendering, or a driver branch. Series densification matches SQL bucket keys to PHP-formatted keys by **string equality**, so the two formats must agree exactly — and an hourly bucket makes any app/DB timezone mismatch displace *every* point, not a minority.
- **`ProxyEventController`'s filter seam has two choke points and one trap.** `applyFilters()` builds the `$start`/`$end` pair **once** and substitutes it into whichever branch it takes (`webhook_events.received_at` when no outcome resolved, the `deliveries`/`delivery_attempts` `updated_at` subquery when one did) — so any change to *what range* the list covers is a one-line substitution there, never a second range clause. But `resolveFilters()` short-circuits to a `null` predicate when the *known* filters all fail to resolve, so **a newly added parameter is silently swallowed unless that condition is widened too**.

**FIFO advancer / claim-lease seam (verified 2026-08-26 while adding Horizon):**
- **The claim lease is stamped once at claim time and never renewed**, and `SweepStalledFifoDispatches` pass (a) reaps every expired `claimed` row unconditionally — it cannot know a worker is still running. `WithoutOverlapping`'s TTL is **deliberately equal** to the lease (`->expireAfter(config('ingest.fifo_lease_seconds'))`), so the overlap lock offers **zero protection past the instant the lease expires**. Nothing in the application closes the concurrency window.
- **The only thing preventing two live advancers is a config value**: Horizon `supervisor-default` `timeout` (60) < `ingest.fifo_lease_seconds` (90), so a worker is killed before its claim is reapable. Full chain `DeliverToDestination::TIMEOUT_SECONDS (15) < supervisor timeout (60) < lease (90) < redis retry_after (180)`. With FIFO's inline sequential fan-out, "timeout must exceed the longest legitimate job" and "timeout must stay under the lease" are **jointly unsatisfiable for ≥5 destinations**.
- **`UNIQUE(delivery_id, attempt_number)` stops a duplicate attempt *row*, never a duplicate *send*.** `DeliverToDestination::resume()` re-drives a row still in status `dispatched` — it cannot distinguish "crashed worker" from "worker sending right now". The guard is scoped to *sequential* at-least-once redelivery only.
- **`AdvanceProxyFifoQueue::settleOrHold()`'s settle branch is a blind `$model->update()` by PK, not a CAS** (its hold branch *is* a CAS). And the whole read-then-write is concurrency-free **only because inline delivery guarantees no delivery of that dispatch can settle concurrently** — min retry delay is ≥1s (`positiveConfigInt` forbids 0). Anything that makes FIFO fan-out queued turns that into a routine race whose losing outcome is a row parked `awaiting_retry` with everything terminal (≤60s stall, sweeper pass (c) releases it).
- **`ingest.fifo_lease_seconds` is a bare `(int) env()` with no `positiveConfigInt()` guard** and is read directly in two places. Blank env ⇒ lease `0` **and** `expireAfter(0)` ⇒ `RedisLock` with **no expiry at all** — instant-reap storm plus a permanently leaked per-proxy lock. Last unguarded config key of that shape.
- **`WithoutOverlapping`'s `$releaseAfter` defaults to `0` and the advancer never calls `->dontRelease()`** — so a losing advancer is released, then fails `MaxAttemptsExceeded` under the supervisors' `tries => 1`. Both `AdvanceProxyFifoQueue`'s docblock and `config/horizon.php`'s production comment claim it is "simply dropped"; it is not.
- **FIFO mode today puts no payload on the queue at all** — the advancer job carries only `int $proxyId`, pipeline entry is by reference, and `DeliverToDestination::run()` is inline. Async serializes the `DeliveryUnit` (payload included) into Redis and thus into `failed_jobs`. Any move to queued FIFO fan-out extends the Q-05-06 D2 / ruling E1 exposure to FIFO — an Owner-gated security consequence, not a free change.
- `DeliverStep` is the terminal pipeline step (`ChangeDetectStep`/#12 is still commented), so no step depends on delivery having completed. Two same-named test classes exist: `tests/Unit/Actions/DeliverStepTest.php` and `tests/Unit/Pipeline/DeliverStepTest.php`.

**Queue-payload seam — what a delivery job carries, and what that costs (verified 2026-08-26):**
- **`RetryDelivery` is the by-reference template and it already exists**: `(deliveryId, attemptNumber)` → reload delivery → guard `payload_cleaned_at` → `terminalizeCleaned()` → destination `withTrashed()` → headers from the event row → bytes from `StoredPayloadLookup::dispatchedBytesFor()`. **ADR-015 Decision 5 already forbids payload bytes in a retry job's arguments** — attempt 1 (`DeliverStep` → `DeliverToDestination::dispatch($unit)`) is the *only* delivery job in the system that carries the payload, and only because #1 predates both the dispatched-output store and the retry path.
- **`dispatchedBytesFor()` ALWAYS resolves — the divergence gate is a positive assertion, not an absence.** `dispatched_payloads.body IS NULL` (or no row at all) *means* "output was byte-identical to the raw capture", so the fallback to `webhook_events.body` is correct rather than a guess. What makes it total: **every payload-mutating step is enhanced-mode-only** (`NormalizeStep` #9, `MapStep` #8 in `PipelineFactory`'s commented contract) **and `CaptureDispatchedStep` — also enhanced-only — is composed last, immediately before `DeliverStep`.** A simple-mode transform step, or a step composed after the capture, would silently deliver stale bytes through any by-reference path.
- **`SerializesModels` DOES reach a laravel-actions job — unlike `ShouldBeEncrypted`.** `JobDecorator` uses the trait (aliasing `__serialize`/`__unserialize`) and its `serializeProperties()` runs `array_walk($this->parameters, …getSerializedPropertyValue(…))`. So a **top-level** model argument becomes a `ModelIdentifier` (class + key + relations + connection, **no attributes**). `array_walk` is one level and `getSerializedPropertyValue()` does **not** recurse — which is why passing a DTO that *holds* a model serializes the whole model, and why today's `dispatch($unit)` puts payload, headers and the full `Destination` into the job. Three vendor behaviours worth knowing: restoration is `Model::newQueryForRestoration()` = `newQueryWithoutScopes()->whereKey()->useWritePdo()->firstOrFail()`, so it **bypasses every global scope** (soft deletes and `TeamScope` alike) and always reads the write connection; and `CallQueuedHandler::handleModelNotFound()` reads **`$job->payload()['deleteWhenMissingModels'] ?? false`** — absent by default, so the default on a missing model is **fail the job**, not delete it, and either way the handler never runs.
- **`ShouldBeEncrypted` does not reach a `lorisleiva/laravel-actions` job.** `Queue::jobShouldBeEncrypted()` tests the serialized object = `Lorisleiva\Actions\Decorators\JobDecorator`, which implements `ShouldQueue` only, declares a fixed public-property set (`$tries`, `$maxExceptions`, `$timeout`, `$deleteWhenMissingModels`) with no `shouldBeEncrypted`, and forwards only an explicit allow-list. Putting the interface on the Action is a **silent no-op**. Reaching it = override `makeJob()` per action, or swap `ActionManager::$jobDecorator` globally (all-or-nothing). Laravel encrypts only `data.command`, never the JSON envelope.
- **Horizon is a second durable store of every job payload.** `JobPayload` keeps the raw string and `RedisJobRepository` writes `$payload->value` verbatim (never decrypts, never unserializes; tags come from the in-memory job pre-serialization). `horizon.trim`: recent/completed 60 min, **failed + monitored 7 days** — a retention `queue:prune-failed` does not touch. So a payload in a job lands in *two* independent 7-day stores.
- Both durable payload stores are already encrypted at rest — `webhook_events.body` (`encrypted`), `.headers` (`encrypted:array`), `dispatched_payloads.body` (`encrypted`) — under **ADR-010 Amendment B's binding `APP_PREVIOUS_KEYS` rule** (never drop a prior key until a re-encryption pass has rehashed every row). `config/app.php` wires `previous_keys`. Encrypting a *queue* message would add a fourth ciphertext location with **no row to re-encrypt**, i.e. a new failure class, not a covered one.
- **Driver-size mismatch, live today on Async:** `ingest.max_body_bytes` defaults to **52,428,800 (50 MiB)** vs **SQS's 256 KiB** message cap — ~200×. Redis (512 MB string) and the `database` driver (`longText`) both tolerate it, which is why it is invisible until a driver change. `queue.default` is `env('QUEUE_CONNECTION', 'database')` while `.env.example` sets `redis`.
- Ordering worth knowing: `queue:prune-failed --hours 168` is a **hard-coded literal in `routes/console.php`** and must stay below `retention.days` (env-overridable, default 30) or a failed job's payload copy outlives the erase meant to destroy it.

**Secret/PII-leak seams discovered while planning #10 (verified 2026-08-27, vendor + `app/`):**
- **`QueryException::formatMessage()` interpolates bindings into the message** — `$previous->getMessage().' (Connection: …, SQL: '.Str::replaceArray('?', $bindings, $sql).')'`. That message reaches `failed_jobs.exception`, **Horizon's own 7-day copy**, and the log. Nothing plaintext leaks today **only because the `encrypted*` casts run at attribute-set time and `Model::performInsert()` binds `$this->getAttributes()`** — so a hand-rolled `Crypt::encryptString()` assignment anywhere would put plaintext into all three. `IngestController:79`'s bare `report($e)` therefore writes *ciphertext* of body+headers into `storage/logs`, a store with no retention pass and no entry in any inventory.
- **`Arr::forget()` supports dot notation but NOT wildcards** (verified in `Illuminate/Collections/Arr.php`), and `Handler::invalid()` flashes `Arr::except($request->input(), $this->dontFlash)`. With `SESSION_DRIVER` defaulting to **`database`**, a submitted secret in a **nested** key (`destinations.*.credential_secret`) lands in the `sessions` table and **`dontFlash` cannot reach it** — needs a `failedValidation()` scrub. Inertia forms never read `old()`, so nothing is lost by scrubbing.
- **`Inertia::flash` → session store; Inertia page props → browser history state.** Neither may carry a secret; a one-time secret reveal must be a plain JSON XHR with `no-store` (the ADR-017 Decision 6 posture, reused).
- **Nothing in `app/` calls `Cache::` or `cache()` at all** — no cache copy of anything, ever (useful for at-rest inventories).
- **Three independent retention literals must stay ordered below `retention.days`**: `queue:prune-failed --hours 168` (a literal in `routes/console.php`), Horizon's `trim.failed`/`recent_failed`/`monitored` = **10080 minutes** (`config/horizon.php`), and `RETENTION_DAYS` (env-overridable). Two literals, one env var, no test.
- **`resources/js/components/PasswordInput.vue` already exists** (masked `Input` + eye/eye-off toggle, no `autocomplete="off"`) — design-10 N3's "no `type="password"` precedent" is factually wrong.
- **`ProxyEventPayloadController` is the only content-bearing response in the system**; `Create.vue` hard-codes blank state and receives **no** proxy resource, so anything the create form needs must be a page prop.
- `destinations`/`proxies` migrations state outright: **soft-deleted, never hard-deleted**, so `cascadeOnDelete` on a child FK never fires — makes FK-integrity arguments weak either way.
- **Portable partial-unique idiom**: `nullable boolean is_current` + `UNIQUE(parent_id, purpose, is_current)` = "at most one current per parent" on MySQL *and* SQLite (both ignore NULLs in unique indexes).
- **"Key absent" vs "key present and null" survives validation and dies one layer later — never build a signal on it.** Verified in vendor: `Validator::validated()` skips any key whose `data_get($this->getData(), $key, $missingValue)` returns the sentinel, and `ValidationData::initializeAndGatherData()` expands `foo.*.bar` into concrete per-row keys against the submitted rows — so an explicit `null` reaches `validated()` and an absent key does not. But **`ProxyController::destinationRows()` normalises every submitted destination field with `isset()`**, which is `false` for an explicit `null`, so the distinction is destroyed in the house normaliser with no error and no failing test. Encode member intent as a **positive value** (a sibling boolean), never as an absence. Wildcard-sibling rule references (`required_with:destinations.*.credential_secret`, `prohibited_if:destinations.*.x,true`) do work and are already used on this form.

**Outbound header seam (verified 2026-08-28, ADR-025):**
- **`DeliveryUnit::STRIPPED_HEADERS` matches five exact provider-signature names, not a category** — `stripe-signature`, `x-hub-signature`, `x-hub-signature-256`, `x-signature`, `x-webhook-signature`. Against 21 real providers that catches **three** (Stripe, GitHub, Intercom); Slack, Shopify, Zoom, PagerDuty, WooCommerce, Xero, Linear, Twitch, Paddle, Square, Discord, SendGrid, Twilio, PayPal **and bare `webhook-signature` (Svix)** have always been forwarded. Any "we strip provider signatures" claim is false.
- **Four distinct `webhook-*` sites, and a global rename breaks two of them.** Outbound emission: `OutboundHeaders::signingHeaders()` (the only one ADR-025 renames, to `WebhookProxy-Id/-Timestamp/-Signature`, hard-coded). Inbound read: `app/Verification/StandardWebhooksScheme.php:37-39`. AC27 inbound strip map: `DeliveryUnitResolver:108`. Header-name-agnostic primitive: `StandardWebhooks::sign($id,$timestamp,$body,$secret)`.
- **Nothing depends on header-name casing**: `OutboundHeaders::withoutNames()` lowercases both sides, `DeliveryUnit::forwardHeaders()` lowercases each inbound name. A test asserting casing tests the wrong property.
- **The Svix collision**: a proxy with no verification configured forwards an inbound `webhook-id/-timestamp/-signature` (AC43), and ADR-023 Decision 2's precedence then **silently destroys** it if that proxy signs — no log, no attempt row, no surface.
- **No source IP anywhere**: `webhook_events` has no such column (create migration + the `2026_08_05_000001` alter are the only two shaping it) and `IngestController` never calls `$request->ip()`. Any `Forwarded`/`X-Forwarded-*` work means new capture + column + retention position.
- Config files are one-per-concern (`ingest`, `retry`, `retention`) with long comment blocks; `RetryPolicy::positiveConfigInt()` is the fail-loud read idiom. `APP_NAME` is still `Laravel` — starter-kit residue, never a product-name source.

**Frontend facts that bite (verified 2026-08-26):**
- **Inertia SSR is `enabled => true` in `config/inertia.php` but there is no `resources/js/ssr.ts`, no `ssr` input in `vite.config.ts` and no `bootstrap/ssr` bundle** — nothing renders server-side; `build:ssr` is starter-kit residue. Treat SSR-safety as contingent, not required.
- **The PR #12 CSS-token colour fix already exists in-repo**: `resources/js/components/welcome/canvasKit.ts` — `readTokens()` reads custom properties verbatim, and `withAlpha()` normalises by round-tripping through a 2D context `fillStyle` because the production minifier rewrites `hsl()` to hex. Reuse the technique; never pattern-match token text.
